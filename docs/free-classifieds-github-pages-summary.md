# Бесплатная доска объявлений на GitHub Pages — архитектурное саммари

## 1. Идея

Сделать бесплатную доску объявлений с добровольными донатами на базе GitHub Pages.

Ключевое ограничение и упрощение:

> Пользователи не публикуют объявления напрямую. Они присылают объявление, а владелец проекта самостоятельно проверяет и публикует его.

Это существенно упрощает архитектуру и делает GitHub Issues подходящим вариантом в качестве CMS/backend для MVP.

---

## 2. Основная архитектура

```text
                 GitHub
        ┌──────────┼──────────┐
        │          │          │
      Issues     Actions     Repo
        │          │          │
        │          ▼          │
        │      listings.json  │
        │          │          │
        └──────────┼──────────┘
                   ▼
             GitHub Pages
                   │
                   ▼
                Web App
```

### Компоненты

- **GitHub Pages** — hosting frontend.
- **GitHub Issues** — объявления и простая CMS.
- **GitHub Labels** — категории, города и статусы.
- **GitHub Actions** — генерация статических данных для сайта.
- **Repository** — код frontend и сгенерированные данные.
- **Донаты** — отдельная внешняя платёжная страница/сервис.

На первом этапе отдельный backend, база данных и авторизация не нужны.

---

# 3. Workflow публикации

Пользователь:

```text
Присылает объявление
        ↓
Владелец проверяет
        ↓
Создаёт GitHub Issue
        ↓
Добавляет labels
        ↓
Прикрепляет фотографии
        ↓
GitHub Action обрабатывает Issue
        ↓
Объявление попадает на сайт
```

Владелец проекта фактически использует GitHub Issues как административную панель.

---

# 4. Структура объявления

Одно объявление = один GitHub Issue.

Пример:

```text
Title:
iPhone 15 Pro 256GB — €650

Labels:
electronics
berlin
active
```

Body:

```text
iPhone 15 Pro 256GB.

Состояние отличное.
Коробка и зарядный кабель в комплекте.

Цена: €650

Связаться:
Telegram: @username
```

Фотографии могут быть прикреплены непосредственно к Issue.

---

# 5. Labels

Labels можно использовать как структурированные данные.

Например:

## Категории

```text
electronics
furniture
cars
services
clothing
other
```

## Города

```text
berlin
hamburg
frankfurt
munich
```

## Статусы

```text
active
sold
expired
```

Важно заранее определить соглашение по labels, чтобы frontend мог однозначно интерпретировать их.

# 6. Почему GitHub Issues подходит

Если объявления публикует только владелец проекта, большинство проблем Issues исчезают.

Не требуется:

- публичный API для создания объявлений;
- регистрация пользователей;
- authentication для продавцов;
- сложная moderation system;
- отдельная admin panel;
- database;
- backend для CRUD объявлений.

GitHub уже предоставляет:

- создание и редактирование Issues;
- удаление/закрытие;
- labels;
- комментарии;
- историю изменений;
- timestamps;
- хранение изображений;
- права доступа;
- базовые механизмы защиты от спама.

Таким образом, GitHub фактически становится бесплатной CMS.

---

# 7. Почему не стоит постоянно обращаться к GitHub API из браузера

Не рекомендуется строить frontend так:

```text
Browser
   ↓
GitHub API
   ↓
получить все Issues
   ↓
фильтровать
```

Причины:

- API rate limits;
- лишняя зависимость frontend от GitHub API;
- дополнительные запросы для каждого посетителя;
- сложнее реализовать быстрый поиск;
- потенциальные проблемы при росте посещаемости.

Лучше использовать GitHub Actions.

---

# 8. Генерация статических данных

Рекомендуемый workflow:

```text
GitHub Issues
      ↓
GitHub Action
      ↓
listings.json
      ↓
GitHub Pages
      ↓
Browser
```

Например:

```json
[
  {
    "id": 152,
    "title": "iPhone 15 Pro 256GB",
    "price": 650,
    "currency": "EUR",
    "city": "Berlin",
    "category": "electronics",
    "status": "active"
  }
]
```

Frontend загружает `listings.json` и работает с ним локально.

В результате обычные посетители сайта не должны обращаться к GitHub API.

---

# 9. URL объявлений

Каждое объявление должно иметь стабильный URL:

```text
/listing/152
```

Например:

```text
https://your-board.github.io/listing/152
```

Это позволяет:

- делиться объявлением;
- отправлять ссылку покупателю;
- использовать объявления в социальных сетях;
- индексировать страницы поисковиками.

# 12. Поиск и фильтрация

Так как данные статические, поиск можно выполнять непосредственно в браузере.

Например:

```text
Текст
Категория
Город
Цена от
Цена до
Статус
```

Frontend загружает `listings.json` и фильтрует данные client-side.

Для небольшого количества объявлений это будет достаточно быстро.

# 13. Модерация

Поскольку объявления публикуются вручную, moderation workflow очень простой:

```text
USER
 ↓
Request
 ↓
MANUAL REVIEW
 ↓
REJECT / ACCEPT
 ↓
GitHub Issue
 ↓
ACTIVE
```

Можно не создавать отдельную систему модерации.

В дальнейшем можно добавить правила:

- запрещённые товары;
- запрещённый контент;
- мошеннические объявления;
- ссылки на вредоносные сайты;
- дубли;
- спам;
- недостоверные цены;
- подозрительные изображения.

---

# 14. Донаты

Донат должен быть добровольным и не обязательным для публикации.

Например:

```text
❤️ Поддержать проект

Этот сервис бесплатный.
Если он оказался полезным,
можно поддержать его развитие.

[ €2 ] [ €5 ] [ €10 ] [ Другая сумма ]
```

Отдельная страница:

```text
/donate
```

И небольшая кнопка в header/footer:

```text
❤️ Donate
```

Потенциальные варианты:

- Stripe Payment Links;
- PayPal;
- Ko-fi;
- Buy Me a Coffee;
- другой доступный платёжный сервис.

На старте достаточно выбрать один.

# 16. Главные ограничения GitHub Issues

Issues всё же не являются полноценной базой данных.

Проблемы появляются при масштабировании:

- сложная фильтрация;
- большое количество объявлений;
- структурированные поля;
- сложные запросы;
- статистика;
- пользователи и аккаунты;
- сложные связи между сущностями;
- автоматизированный CRUD;
- большое количество изображений.

Поэтому Issues следует рассматривать как **MVP CMS**, а не как вечную database architecture.

# 17. Когда мигрировать с Issues

Если проект начнёт расти, можно перейти на:

```text
GitHub Pages
      +
Cloudflare Worker
      +
Cloudflare D1
      +
Cloudflare R2
```

При этом frontend можно сохранить практически без изменений.

Миграция будет выглядеть так:

```text
                    MVP

GitHub Issues
      ↓
GitHub Actions
      ↓
listings.json
      ↓
GitHub Pages


                    ↓

                 Growth


GitHub Pages
      ↓
Cloudflare Worker
      ↓
D1 + R2
```

То есть MVP не должен создавать архитектурный тупик.

# 19. Ключевой архитектурный принцип

Не строить backend заранее.

Поскольку владелец проекта сам принимает и публикует объявления, GitHub уже выполняет роль:

```text
CMS
+
storage
+
moderation
+
version history
+
admin interface
```

А GitHub Pages отвечает только за публичный frontend.

Это позволяет сделать сервис:

- бесплатным;
- очень дешёвым в эксплуатации;
- простым в разработке;
- простым в поддержке;
- легко масштабируемым при необходимости.

## Вывод

Для модели **«пользователь присылает объявление → я проверяю → сам публикую»** GitHub Issues — не компромисс, а вполне рациональный выбор для MVP.

Не нужно преждевременно добавлять:

- PostgreSQL;
- отдельный backend;
- authentication;
- admin panel;
- cloud storage;
- сложную moderation system.

Сначала стоит сделать максимально простой static marketplace и проверить реальный спрос. Если появится нагрузка — заменить GitHub Issues на полноценный backend уже тогда.
